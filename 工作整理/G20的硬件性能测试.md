## G20图传 TCP测试
![[Pasted image 20260827144133.png|475]]

![[Pasted image 20260827144214.png|475]]

**现象 1**：30 秒测试中约有 15 秒的区间显示 `0.00 Bytes 0.00 bits/sec`（完全零流量），且这些零流量区间穿插在有数据的区间之间，没有规律地反复出现。
**结论 1**：图传链路存在间歇性的完全阻塞窗口，数据在这些时间段内完全无法通过，不是持续可用的稳定链路。

**现象 2**：`Retr`（重传）列在 30 秒内累计出现 55 次重传，部分秒内重传数高达 14、18 次。
**结论 2**：链路存在真实的丢包，TCP 检测到丢包后触发重传机制，这是导致发送侧数据滞留、间隔变长的直接原因之一。

**现象 3**：拥塞窗口（Cwnd）从 27.8KB 一路涨到 80.4KB，随后因重传骤降到 30~40KB 反复震荡。
**结论 3**：TCP 的拥塞控制在不断"探测-回退"，每次回退都会降低发送速率，进一步放大了分片之间的等待时间。

**现象 4**：整体平均吞吐仅 175~318 Kbits/sec，远低于图传链路正常应有的带宽水平。
**结论 4**：该链路对这条数据流的实际可用带宽被严重压低，不是 SDK 或应用层的问题，而是传输链路层面的限制。

## G20图传 UDP测试
![[Pasted image 20260827144543.png|450]]
![[Pasted image 20260827144507.png|475]]
**现象 1**：Jitter（抖动）从 0ms 持续、近乎线性地爬升到 60 秒时的 136ms，全程没有回落。
**结论 1**：典型的"缓冲区膨胀"（Bufferbloat）特征——链路中存在一个队列在持续积压数据包，排队时间越来越长，而非普通无线干扰引起的随机抖动（随机干扰应表现为忽高忽低而非单调爬升）。

**现象 2**：丢包并非随机分布，而是大约每 6~7 秒出现一次（17s、23s、30s、36s、43s、49s、56s），共 7 次，整体丢包率 7.6%。
**结论 2**：丢包具有明显的周期性规律，很可能源自图传链路本身固定周期的调度行为（如跳频、TDD 时隙切换、周期性同步/心跳占用信道等），而不是环境噪声导致的偶发丢包。

**现象 3**：发送端（遥控器）全程 0 丢包、速率稳定，但接收端（机器人）测得的丢包和高抖动，两端数据不一致。
**结论 3**：问题发生在数据从遥控器传输到机器人的链路中间环节（即图传无线传输本身），而不是发送端或接收端设备自身的处理问题。

## 对硬件（图传模块/链路）的结论

**现象 1**：TCP 测试的间歇性完全阻塞 + UDP 测试的周期性丢包（约 6~7 秒一次）+ 持续爬升的抖动，三者相互印证，都指向同一个规律性行为。
**结论 1**：图传硬件/模组内部存在周期性的信道调度机制（如跳频、TDD 切换或同步开销），该机制会周期性挤占或阻塞数据传输通道，导致音频这种小数据量、时延敏感的流量被间歇性延迟或丢弃。

**现象 2**：链路实测吞吐（175~318 Kbps）远低于该类图传设备通常应具备的带宽能力。
**结论 2**：当前链路很可能没有针对音频等小流量数据做优先级保障（QoS），在与视频等大流量数据共享信道时容易被挤占，或者链路本身的缓冲策略不适合低延迟小包场景。

### 现象与结论

**现象 1**：两次测试中各出现 2 个完全零吞吐的 1 秒区间（共 4 次），但每次仅持续 1 秒，之后立即恢复。
**结论 1**：零吞吐区间短暂（1 秒级别），与图传链路中大量穿插的零流量窗口有本质区别，很可能是 WiFi 省电模式（PSM, Power Save Mode）触发设备休眠一个 Beacon 周期后恢复，或 WiFi 驱动层偶发调度暂停，整体链路连通性良好。

**现象 2**：TCP 重传极少（30 秒内累计 0~1 次），与图传 TCP 测试的 55 次重传形成鲜明对比。
**结论 2**：WiFi 链路的丢包率极低，接近无损传输，TCP 拥塞控制几乎没有触发回退行为，链路物理层质量明显优于图传模组。

**现象 3**：拥塞窗口（Cwnd）在 3~4 秒内迅速增长并稳定在最大值 1.92 MB，此后全程维持不变。
**结论 3**：TCP 发送侧完全不受拥塞控制限制，瓶颈纯粹在 WiFi 无线媒介的实际传输速率上，而非 TCP 协议层问题。

**现象 4**：每秒吞吐量在约 8~9 Mbits/sec 与约 17~23 Mbits/sec 之间交替波动，呈现明显的"快-慢"交替节律。
**结论 4**：典型的 WiFi 速率自适应（Rate Adaptation / MCS 切换）行为——无线信道条件在小幅波动时，驱动层在高 MCS 和低 MCS 之间来回切换，导致逐秒吞吐显著振荡，但时间均值稳定在 11 Mbits/sec 左右。

**现象 5**：服务端（机器狗）接收侧的逐秒数据比客户端（G20）更平滑，客户端显示 0 Bytes 的区间，服务端仍能收到少量数据（如第一次测试服务端全程无零值区间）。
**结论 5**：WiFi 子系统在 G20 发送侧发生短暂暂停时，已缓冲的数据仍在持续传出；数据并未真正丢失，只是被短暂积压在 WiFi 驱动/硬件缓冲区中，体现为客户端发送侧的瞬时零报告，而非实际断流。

## 掌机设备 WIFI TCP测试（干扰较多环境）
> 同一台掌机设备（mt6877_fhd_v1，192.168.144.2），连续进行 4 次测试，前两次表现优异，后两次出现极端退化。
### 整体指标

| 指标 | 第1次测试 | 第2次测试 | 第3次测试 | 第4次测试 |
|------|----------|----------|----------|----------|
| 发送端平均吞吐 | **105 Mbits/sec** | **89.5 Mbits/sec** | 5.49 Mbits/sec | 1.75 Mbits/sec |
| 接收端平均吞吐 | **105 Mbits/sec** | **89.1 Mbits/sec** | 4.22 Mbits/sec | 1.66 Mbits/sec |
| 总重传次数（Retr） | 47 | 26 | 17 | **61** |
| 零吞吐区间次数 | 0 | 0 | **~19 次** | **~2 次** |
| 最终 Cwnd | 2.41 MBytes | 2.32 MBytes | 1.16 MBytes | **48.1 KBytes** |
| 接收端完成时间 | 30.06s | 30.16s | **36.55s** | 30.42s |

---
### 现象与结论

**现象 1**：前两次测试吞吐分别为 105 Mbits/sec 和 89.5 Mbits/sec，后两次骤降至 5.49 Mbits/sec 和 1.75 Mbits/sec，同一设备、同一网络下相差最高约 **60 倍**。
**结论 1**：问题是 WiFi 的 **TX 速率自适应算法**（Rate Adaptation / MRA）因某次信道质量波动一路退到 MCS0，之后没能恢复——即使环境已改善（RSSI 甚至更好），算法仍卡在最低速率档位。重连wifi之后恢复了正常

**现象 2**（第 4 次测试）：Cwnd 全程在 15~120 KBytes 的极低水平振荡，从未超过 150 KB（正常测试约 3 MB），每秒均有重传，部分秒内重传高达 9 次，且 Cwnd 越来越小（到第 21 秒跌至 15.6 KBytes）。
**结论 2**：链路处于**持续严重丢包**状态，TCP 的每一次慢启动都因新的丢包而被打断，Cwnd 完全无法扩大。极低的 Cwnd（15 KB ≈ 约 10 个 MTU）意味着每个 RTT 内只能在途极少量数据，吞吐被压制到物理极限以下（1.75 Mbits/sec），链路实际上已处于不可用状态。

**现象 3**：第 3 次测试的 17 次重传中，有多次发生在 Cwnd 已经很小时（如 25-26s 出现 1 次重传后 Cwnd 从 882KB → 638KB），每次重传都触发进一步的窗口缩小，形成**恶性循环**。
**结论 3**：丢包率超过 TCP 拥塞控制的承受能力，导致正反馈式的性能崩溃。这不是普通的信道波动，而是 **链路级别的周期性或持续性不可用**——数据包在空口被大量丢弃，TCP 层不断响应但无法恢复。

### 对掌机设备 WiFi 稳定性的综合结论

| 维度 | 正常状态（测试 1~2） | 退化状态（测试 3~4） |
|------|-------------------|-------------------|
| 平均吞吐 | 89~105 Mbits/sec | 1.75~5.49 Mbits/sec |
| Cwnd | 2.4~3.0 MBytes（稳定） | 持续萎缩 / 极低振荡 |
| TCP 行为 | 正常拥塞控制 | RTO 超时 + 恶性循环崩溃 |
| 零吞吐区间 | 无 | 大量（占 60%+ 秒数） |

掌机 WiFi 存在**状态双峰**特征：要么运行在高吞吐的稳定模式（~100 Mbits/sec），要么陷入完全崩溃的退化模式（~2 Mbits/sec），两者之间缺乏平稳过渡。通过退化期间采集的 `cmd wifi status` 数据确认（BSSID 和 Frequency 5180MHz 与正常时完全相同），**可排除频段切换（5GHz↔2.4GHz）**，实际原因是 **TX 速率自适应算法卡死在 MCS0（HE MCS0 80MHz = 36 Mbps 理论值）**，重连 WiFi 重置关联和算法状态后立即恢复正常。在退化状态下用于对时延/丢包敏感的实时控制场景是不可接受的。

## G20 与掌机 WiFi 硬件能力对比分析
> 依据：退化期间及恢复后采集的 `cmd wifi status` 数据，结合 iperf3 吞吐结果。
### 硬件能力基线对比

| 指标                | G20（bengal_515）       | 掌机（mt6877_fhd_v1）     |
| ----------------- | --------------------- | --------------------- |
| Wi-Fi 标准          | **Wi-Fi 5**（802.11ac） | **Wi-Fi 6**（802.11ax） |
| 天线配置              | 1×1（单流）               | 2×2（双流）               |
| Max Tx Link speed | **433 Mbps**          | **1200 Mbps**         |
| Max Rx Link speed | **433 Mbps**          | **1200 Mbps**         |
| iperf3 正常吞吐       | ~11 Mbits/sec         | ~37~105 Mbits/sec     |

G20 的硬件上限（433 Mbps = VHT MCS9 NSS1 80MHz）是掌机（1200 Mbps = HE MCS11 NSS2 80MHz）的约 1/3，代差一个 WiFi 世代（5 vs 6），且少一根天线（1×1 vs 2×2）。
### G20 TX/RX 严重不对称的证据
退化期间 G20 的实测数据：
```
Tx Link speed:  6 Mbps   ← G20 → AP 方向，VHT MCS0
Rx Link speed: 87 Mbps   ← AP → G20 方向，正常
retriedTxPackets:  11123
successfulTxPackets: 1030   ← 重试次数是成功的 10 倍
lostTxPackets: 78
RSSI: -47 dBm             ← 信号强度良好，非覆盖问题
```
**现象**：RSSI -47 dBm（优秀），但 TX 仅 6 Mbps、RX 达 87 Mbps，双向差距达 14 倍，空口重试率极高（重试/成功 ≈ 10:1）。
**结论**：问题不在信号强度，而在 G20 的**发射链路**（TX chain）本身——天线增益、发射功率或芯片发射路径质量低于接收路径，AP 侧天线增益更高因此能正常接收 G20 的弱发射，但 G20 发送时 AP 无法以高 MCS 确认接收，迫使速率回退到 MCS0
### MCS 退化机制对比
MCS（Modulation and Coding Scheme）是 WiFi 发送数据时的调制与编码方案，索引越高数据密度越大，对信道质量要求也越高。速率自适应算法根据空口误包率（PER）动态调整 MCS：误包率高则降档，误包率低则升档。

| 状态   | G20 Tx MCS   | 对应速率         | 掌机 Tx MCS | 对应速率      |
| ---- | ------------ | ------------ | --------- | --------- |
| 退化时  | VHT MCS0     | 6 Mbps       | HE MCS0   | 36 Mbps   |
| 正常时  | 偏低（约 MCS2~3） | ~11 Mbps（均值） | HE MCS5   | 288 Mbps  |
| 硬件上限 | VHT MCS9     | 433 Mbps     | HE MCS11  | 1200 Mbps |

两台设备退化时都落到各自标准的 **MCS0**，但因世代不同，G20 的 MCS0 = 6 Mbps，掌机的 MCS0 = 36 Mbps。掌机退化后重连可恢复是驱动/固件层面的速率算法问题；G20 的低吞吐更根本——即使算法正常，TX 硬件质量限制了能稳定使用的 MCS 上限。
### 综合结论
**G20 WiFi 性能低的根本原因是硬件能力而非环境因素**：Wi-Fi 5 单流芯片、TX 链路质量弱（高重试率、TX/RX 严重不对称），导致实际可用吞吐仅约 11 Mbits/sec，且发送方向空口质量差。这是芯片/天线方案选型层面的差距，无法通过软件或配置弥补，在需要稳定高吞吐双向通信的机器人控制场景中是实质性的硬件短板。

## 结论
综上，G20 WiFi 芯片：Qualcomm WCN3988，是高通 bengal 平台的**随 SoC 集成的低端 WiFi 模块**，主要设计目标是功耗和成本，而非性能，最大速率是**433 Mbps**。导致G20的wifi表现比较差，在干扰较多的环境下，协商发送速率为6Mbps，实际可用带宽跌破 1 Mbps，平均吞吐仅 664 Kbits/sec，30 秒内有 ~24 秒为零吞吐（占 80%），还有48 次 TCP 重传。

在低干扰环境下，G20 的 WiFi 链路稳定、丢包极低，**满足轻量级数据上报场景的需求**。一旦进入高干扰或信道竞争环境，TX 发射链路弱的固有缺陷会放大退化幅度（如之前观测到的降至 664 Kbits/sec 甚至更低），稳定性边界比掌机等 WiFi 6 设备更窄。
